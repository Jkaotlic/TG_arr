# TorrServer в TG_arr: кнопка «Смотреть» и принудительная публикация в Emby

Дата: 2026-08-05
Статус: одобрено пользователем, готово к плану

## Зачем

TorrServer (`192.168.31.95:8090`, MatriX.142.2) отдаёт торренты HTTP-потоком без
скачивания на диск. Витрину в Emby делает скрипт `Sync-TorrServerToEmby.py` на
Homeserver: раскладывает `.strm` по `G:\torrstream\{Films,Series}`, в конце дёргает
`POST /Library/Refresh`. Запускается задачей `TorrServer-EmbySync` раз в 10 минут.

Сейчас добавить раздачу можно только из веб-морды TorrServer или Lampa, и потом
ждать до 10 минут, пока она появится в Emby. Бот TG_arr — единственная точка, из
которой пользователь и так управляет медиастеком, и её не хватает для сценария
«хочу посмотреть это сейчас, а не иметь в библиотеке».

Scryer-контур («хочу иметь») остаётся нетронутым. TorrServer — параллельный
контур «хочу посмотреть сейчас».

## Область работ

**Входит:** клиент TorrServer в боте; свой поиск раздач через torznab TorrServer;
добавление раздачи; принудительный запуск синка в Emby через новый HTTP-хук на
Homeserver; список раздач и удаление; карточка статуса TorrServer и его учёт в
`/status`; ссылка на поток в ответе после добавления.

**Не входит:** изменение существующего поиска через Scryer; работа с музыкой;
кнопка «Смотреть сейчас» в карточке релиза Scryer-поиска; ручная кнопка
«Синхронизировать с Emby» отдельно от добавления; изменение самого скрипта
`Sync-TorrServerToEmby.py` и его расписания.

## Факты, проверенные на живой системе 2026-08-05

Опираться на них при реализации; всё остальное — сверять, а не додумывать.

- `GET /echo` → `MatriX.142.2`, без авторизации. Доступен с rpie4.
- Остальной API — Basic-авторизация, `admin` + пароль из
  `C:\Tools\TorrServer\secrets\admin-password.txt`.
- `POST /torrents` с телом `{"action":"list"}` → массив объектов с полями
  `title`, `category` (`movie` / `tv`), `poster`, `data`, `timestamp`, `hash`,
  `stat`, `stat_string`, `torrent_size`. На момент проверки — 5 раздач.
- `data` — **строка** с JSON вида `{"TorrServer":{"Files":[{"id","path","length"},…]}}`.
  У BD-ремукса это 271 запись; в модель бота целиком не тащить.
- Поиск: `GET /torznab/search/?query=<строка>` — параметр берётся из query-string.
  Форма `/torznab/search/<строка>` уходит **пустым запросом** и возвращает RSS
  последних раздач: выглядит как «поиск работает, но нерелевантно».
- Ссылка на поток (форма взята из работающего скрипта синка):
  `http://192.168.31.95:8090/stream/<urlquote(имя файла)>?link=<hash>&index=<file_id>&play`
- Задача `TorrServer-EmbySync` существует, статус Ready, интервал 10 минут.
- `Sync-TorrServerToEmby.py --apply` сам вызывает `POST /Library/Refresh` Emby —
  боту отдельный скан Emby делать не нужно.
- Скрипт синка определяет тип контента **по имени файла**: regex `s(\d{1,2})e(\d{1,3})`
  → `Series\<Шоу>\Season NN\`, иначе → `Films\<Название раздачи>\`. Бот не должен
  спрашивать у пользователя «фильм или сериал».
- В контейнере бота на rpie4 нет ни `ssh`, ни `curl`; есть httpx 0.28.1.

Контракт мутирующих вызовов снят пробой на живом сервере 2026-08-05 (проба
добавлена и удалена, постусловие проверено — её хеша в `list` нет):

- `{"action":"add","link":…,"title":…,"poster":…,"save_to_db":true}` → объект
  раздачи; сразу после добавления `stat: 1`, `stat_string: "Torrent getting info"`,
  `torrent_size: null`.
- `{"action":"get","hash":…}` → полный объект: `active_peers`, `bytes_read`,
  `bytes_written`, `category`, `connected_seeders`, `data`, `file_stats`,
  `hash`, `name`, `poster`, `stat`, `stat_string`, `timestamp`, `title`,
  `torrent_size`, `total_peers`. Через несколько секунд `stat: 3`,
  `stat_string: "Torrent working"`, появляется `name` и `torrent_size`.
- `file_stats` активной раздачи — массив `{"id","path","length"}`. Это и есть
  сигнал «метаданные пришли», по которому бот перестаёт ждать.
- `{"action":"rem","hash":…}` → пустой ответ, раздача исчезает из `list`.
- `POST /settings` с `{"action":"get"}` → объект настроек: `CacheSize`
  (1610612736), `UseDisk` (false), `ConnectionsLimit` (100),
  `TorrentDisconnectTimeout`, `EnableDLNA`, `FriendlyName`, а также
  `TorznabUrls` — массив `{Host,Key,Name}`. Отдельного эндпоинта со счётчиком
  активных потоков нет, поэтому в карточку статуса он не выносится.

**Поиск отдаёт JSON, а не RSS** (проверено тем же днём). `GET /torznab/search/?query=Interstellar`
→ массив объектов:

| поле | смысл |
| --- | --- |
| `Title`, `Name` | название раздачи |
| `Size` | **строка** вида `"2.5 GCiB"` — не число |
| `Seed`, `Peer` | сиды и пиры |
| `Link` | ссылка на скачивание через Prowlarr с `apikey`; её и отдаём в `add` |
| `Magnet` | часто пустая — опираться на `Link` |
| `Tracker` | часто пустая; имя индексера восстанавливается по номеру в `Link` |
| `Year`, `IMDBID`, `Categories`, `CreateDate` | вспомогательные, часто пустые |

Ответ на один запрос — около 470 КБ, поэтому разбор сразу режет список до
показываемого объёма и не хранит сырой ответ.

Имя индексера: `Link` имеет вид `http://192.168.31.95:9696/<id>/download?…`, а
`TorznabUrls` из настроек содержит `Host` с тем же `<id>` на конце и `Name`.
Клиент строит карту id → имя по настройкам (кеш на 10 минут через
`BaseAPIClient._ttl_cached`) и подставляет её, когда `Tracker` пуст. На
2026-08-05 подключено 6 источников: Kinozal, RuTracker.org, RinTor.NeT,
OpenSharing, Knaben, The Pirate Bay.

## Решения, принятые в брейнсторме

1. Отдельная кнопка главного меню со **своим** поиском по torznab TorrServer, а не
   вторая кнопка в карточке релиза Scryer-поиска.
2. Принудительный синк — через **HTTP-хук на Homeserver**, а не SSH из контейнера
   и не учащение задачи планировщика.
3. В разделе есть: список раздач с удалением, карточка статуса сервера и кеша,
   ссылка на поток в ответе после добавления. Отдельной кнопки ручного синка нет.
4. Запрос для TorrServer-поиска вводится ответом на сообщение с **ForceReply** —
   без состояния в БД и без гонки с обычным текстовым поиском.

## Архитектура

### Бот (слой 1 — TDD обязателен)

```text
bot/clients/torrserver.py       TorrServerClient        — HTTP к TorrServer
bot/clients/emby_sync_hook.py   EmbySyncHookClient      — HTTP к хуку на Homeserver
bot/services/torrserver_service.py TorrServerService    — сценарий «добавить и опубликовать»
```

Правки существующего:

- `bot/config.py` — новые поля и свойства (ниже), плюс предупреждение о
  полу-настроенной интеграции по образцу `_warn_on_inconsistent_integration_config`.
- `bot/clients/registry.py` — `get_torrserver()`, `get_emby_sync_hook()` с
  собственными `asyncio.Lock`, закрытие в `close_all()`.
- `bot/ui/menu.py` — `MENU_TORRSERVER = "▶️ Смотреть"`, добавить в `MENU_BUTTONS`.
- `bot/ui/keyboards/menu.py` — кнопка в раскладке (четвёртый ряд, рядом с «История»).
- `bot/handlers/__init__.py` — `torrserver_router` включается **после `start_router`
  и до `search_router`**: `handle_text_search` в search перехватывает любой текст,
  а aiogram не каскадирует обработчики после совпадения (см. BUG-27 в grab.py).
- `bot/handlers/status.py` — TorrServer в общей карточке статуса.

### Хук на Homeserver (слой 3 — инфра-скрипт, без TDD)

```text
C:\Tools\TorrServer\Emby-Sync-Hook.py      служба HTTP
C:\Tools\TorrServer\Install-EmbySyncHook.ps1  идемпотентный установщик
C:\Tools\TorrServer\secrets\hook-token.txt    токен
```

- Служба NSSM `TorrServerEmbySyncHook`, LocalSystem, AUTO_START, слушает
  `0.0.0.0:8099`, лог `C:\Tools\TorrServer\logs\emby-sync-hook.log`.
- `POST /sync` с заголовком `X-Token` → запускает `Sync-TorrServerToEmby.py --apply`.
  Ответ `200 {"status":"ok","duration_s":N}`.
- Синк уже идёт → `202 {"status":"already_running"}`, второй процесс не плодится.
- Неверный или отсутствующий токен → `403`, тело пустое, факт пишется в лог.
- `GET /health` → `200 {"status":"ok"}` без токена — для проб бота и Gatus.
- Установщик идемпотентен: повторный запуск не ломает существующую службу; токен
  генерируется только если файла ещё нет. Постусловие проверяется явно: служба в
  `SERVICE_RUNNING`, `GET /health` → 200, `POST /sync` с валидным токеном → 200.

| `EMBY_SYNC_HOOK_TOKEN` | токен хука |

Свойства `Settings`:

- `torrserver_enabled` — заданы url, username и password.
- `emby_sync_hook_enabled` — заданы url и token.

Предупреждения (не ошибки, бот должен стартовать): полу-заданный TorrServer;
полу-заданный хук; `torrserver_enabled` без `emby_sync_hook_enabled` —
«раздачи будут добавляться, но в Emby попадут только штатной задачей раз в 10 минут».

## Пользовательские сценарии

### Панель

Кнопка «▶️ Смотреть» или `/ts` → карточка: версия TorrServer, число раздач, суммарный
размер, размер и режим кеша, число активных потоков. Кнопки:
`🔎 Найти` · `📋 Раздачи` · `🔄 Обновить` · `✖️ Закрыть`.

TorrServer не настроен → кнопки в меню нет; `/ts` отвечает подсказкой про переменные
окружения (по образцу «Emby не настроен»). Сервер не отвечает → карточка ошибки с
кнопкой «Обновить», раздел не падает.

### Поиск и добавление

1. `🔎 Найти` → сообщение с точным текстом-маркером
   `▶️ Что найти в TorrServer?` и `ForceReply(input_field_placeholder="Название раздачи")`.
2. Ответ пользователя ловится фильтром `F.reply_to_message.text == "▶️ Что найти в TorrServer?"`.
   Маркер объявляется константой в `bot/ui/menu.py` рядом с `MENU_TORRSERVER`, чтобы
   текст сообщения и фильтр не разъехались (та же причина, по которой там уже живут
   `MENU_*`).
   Пустой запрос или короче 2 символов → просьба повторить.
3. `GET /torznab/search/?query=…`, разбор JSON-массива (см. таблицу полей выше;
   `Size` парсится из строки, имя индексера восстанавливается по `Link`).
   Результаты сортируются по сидам по убыванию, режутся до 30, показываются
   страницами по `RESULTS_PER_PAGE` (5).
   Пустая выдача → «ничего не найдено», кнопка «Искать ещё раз».
4. Строка результата: название (обрезанное), размер, сиды, индексер.
5. Выбор → карточка раздачи с кнопками `▶️ Смотреть` и `⬅️ Назад`.
6. `▶️ Смотреть` → `TorrServerService.add_and_publish()`:
   - название чистится от `/`, `\` и управляющих символов (замена на ` - `) **до**
     добавления — иначе листинг WebDAV/DLNA этой категории отдаёт 500 и папка
     выглядит пустой, и придётся ждать `TorrServer-SanitizeTitles`;
   - `POST /torrents` action=add с ссылкой, очищенным названием и постером;
   - поллинг `action: get` по хешу, пока не появятся `Files`, не дольше
     `TORRSERVER_METADATA_TIMEOUT` (интервал 2 с);
   - при наличии файлов — `POST /sync` на хук;
   - ответ пользователю: название, размер, список видеофайлов (до 10, остальные
     «и ещё N»), прямая ссылка на поток первого видеофайла, строка про Emby.
7. Ошибки не отменяют друг друга:
   - метаданные не пришли за таймаут → «раздача добавлена, файлы ещё подтягиваются,
     в Emby попадёт штатной задачей в течение 10 минут»;
   - хук недоступен, вернул 403 или 5xx → «раздача добавлена, синхронизация не
     запустилась: <причина>; в Emby попадёт в течение 10 минут»;
   - хук ответил 202 → «синхронизация уже идёт».
   - добавление не удалось → карточка ошибки, кнопка «Назад к результатам».

Пагинация, callback-данные и хранение результатов поиска — в сессии SQLite по
образцу Scryer-поиска, но со **своими** моделями: `SearchResult` завязан на
Scryer (`candidate_token`, `scryer_*`), переиспользовать его нельзя.

### Список раздач и удаление

`📋 Раздачи` → страницы по 5: название, размер, категория, число файлов, статус
(`stat_string`). У каждой — кнопка `🗑` (только админам; не-админу — alert
«Недостаточно прав»). Нажатие → подтверждение `Удалить?` / `Отмена`, затем
`action: rem` по хешу и обновление списка.

Удаление раздачи не удаляет её `.strm` немедленно — это сделает ближайший проход
скрипта синка. Бот честно пишет: «раздача удалена, из Emby пропадёт в течение
10 минут». Дёргать хук на удалении не нужно.

## Модели данных

```text
TorrServerRelease   — результат поиска: title, size, seeders, indexer, link, publish_date
TorrServerFile      — id, path, length
TorrServerTorrent   — hash, title, category, poster, size, stat, stat_string, files
TorrServerStats     — version, torrent_count, total_size, cache_size, use_disk, active_streams
SyncHookResult      — status (ok / already_running / failed), duration_s, error
```

`TorrServerTorrent.files` заполняется разбором строки `data`; в списке раздач
используется только их количество и суммарный размер, полные пути — только в
ответе после добавления, где показываются видеофайлы (расширения `.mkv`, `.mp4`,
`.avi`, `.ts`, `.m2ts`, `.mov`, `.wmv`), отсортированные по размеру.

## Права

Поиск, добавление, просмотр списка и статуса — всем из `ALLOWED_TG_IDS`.
Удаление раздачи — только `ADMIN_TG_IDS`, как остальная деструктивная механика бота.

## Тестирование

Бот (обязательно до кода, TDD):

- Клиент: разбор JSON-выдачи поиска, включая `Size` вида `"2.5 GCiB"` и пустой
  `Tracker` (имя берётся из карты по `Link`); пустая выдача; 401 → своя ошибка;
  таймаут → своя ошибка; разбор `data` со списком файлов; элемент списка с
  `data`, которое не парсится (не должно ронять весь список).
- Отдельный тест-страж: запрос уходит **в query-string**, а не в путь.
- Санитизация названия: `Холодное сердце 2 / Frozen II […]` → без слэшей.
- Сервис: успешный сценарий; метаданные не пришли за таймаут; хук вернул 403 / 5xx /
  202 — во всех случаях добавление считается успешным, меняется только текст ответа.
- Хендлеры: панель при выключенной интеграции; ForceReply-ответ уходит в
  TorrServer-поиск, а обычный текст — в Scryer-поиск; удаление не-админом отбивается.

Моки — `unittest.mock.AsyncMock`/`MagicMock` и monkeypatch, как во всех
существующих тестах клиентов (`respx` в проекте нет и не добавляется). Сеть в
тестах не используется.

Хук на Homeserver (слой 3, вместо TDD — постусловие):

1. До: `.strm` для тестовой раздачи нет.
2. `POST /sync` с валидным токеном → `200`.
3. После: файл `.strm` появился, в `emby-sync.log` строка `Emby refresh -> HTTP`.
4. `POST /sync` без токена → `403`. Повторный запуск установщика не меняет состояние
   службы.

## Готовность

`make test` зелёный и `make lint` чистый с показанным выводом; сквозной живой
сценарий на деплое: кнопка → поиск → добавление → раздача видна в
`POST /torrents` list → `.strm` появился на Homeserver → элемент виден в библиотеке
Emby «Торренты (фильмы)» или «Торренты (сериалы)».

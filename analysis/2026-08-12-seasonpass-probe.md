# Что на самом деле делает `POST /api/v3/seasonpass` в Sonarr

- **Дата:** 2026-08-12
- **Sonarr:** 4.0.19.2979 (живой стек, `192.168.0.95:8989`)
- **Зачем:** `SonarrClient.set_season_monitoring` (задача 3 плана
  `docs/superpowers/plans/2026-08-12-five-improvements.md`) делегирует смысл
  пресета мониторинга самому Sonarr. Прежде чем писать клиент под этот
  эндпоинт, надо было убедиться, что он делает то, ради чего его берут.
- **Слой 4** (эксплуатация живой системы). TDD неприменим; гарантия — **проверка
  постусловия**: снять состояние ДО → применить → сверить ПОСЛЕ → вернуть как
  было → убедиться, что вернулось.

## Метод и путь

Пробник по существованию маршрута — no-op по построению: пустой список `series`
не может задеть ни один сериал.

```text
POST /api/v3/seasonpass  ->  202 Accepted, тело {}
PUT  /api/v3/seasonpass  ->  405 Method Not Allowed
```

Метод — **POST**. Тело ответа пустое, поэтому судить об успехе по содержимому
нельзя: критерий — отсутствие HTTP-ошибки.

Форма запроса:

```json
{"series": [{"id": 30}], "monitoringOptions": {"monitor": "future"}}
```

Открыть `/docs/v3/openapi.json` не вышло: этот путь требует UI-авторизации, а не
`X-Api-Key` (401 с ключом в заголовке и с ключом в query). `GET` по несуществующему
маршруту Sonarr отдаёт 404, как и по существующему, — отличить наличие маршрута
чтением нельзя, поэтому проверка шла записью.

## Подопытный

**Silo**, `id=30`, `status=continuing`, 34 эпизода в 4 «сезонах» (включая нулевой).
Выбран за то, что идёт прямо сейчас: разница между «будущими» и «вышедшими»
сериями на нём наблюдаема. Сегодня 2026-08-12.

Состояние ДО:

| | |
|---|---|
| `series.monitored` | `True` |
| сезоны | `[(0, False), (1, False), (2, False), (3, True)]` |
| эпизоды | 8/34 промониторено, все в сезоне 3 |

Полный снимок (объект сериала + флаг каждого эпизода) сохранялся на диск перед
мутацией, чтобы возврат можно было повторить независимо от исхода.

## Что измерено

### 1. `monitor="future"` переставляет флаги ЭПИЗОДОВ, а не только сезонов

| | сезоны | эпизоды |
|---|---|---|
| до | `[(0,F),(1,F),(2,F),(3,T)]` | 8/34 |
| после | `[(0,F),(1,F),(2,F),(3,T)]` | **4/34** |

Осталось промониторено ровно то, что ещё не вышло: S3E7 (14.08), S3E8 (21.08),
S3E9 (28.08), S3E10 (04.09). Четыре уже вышедших эпизода сезона 3 сняты.

Это и был главный вопрос: клиентская переработка семантики через
`_should_monitor_season` дала бы для `future` немониторимыми **все** сезоны — то
есть воспроизвела бы чинимый дефект.

### 2. Эндпоинт вытаскивает сериал из состояния `monitor="none"`

Именно оно и есть производственный старт: `_resolve_arr_entry` добавляет тайтл
с `monitored=False, monitor="none"`, чтобы простой просмотр релизов не втянул
шоу в RSS-петлю. Проверена точная последовательность:

| шаг | сезоны | эпизоды |
|---|---|---|
| `seasonpass none` | все `False` | 0/34 |
| `seasonpass future` поверх | сезон 3 → **`True`** | **4/34** |

Из полностью немониторимого состояния `future` поднимает и сезонный флаг, и
флаги будущих эпизодов. Значит связка «добавили с `none` → при грабе применили
пресет» работает, и новые серии будут подхватываться.

## Возврат

Восстановление: `PUT /api/v3/series/30` сохранённым объектом (сезонные флаги),
затем `PUT /api/v3/episode/monitor` двумя группами (промониторенные → `true`,
остальные → `false`). Порядок важен: сезонные флаги первыми, иначе их установка
перетирает эпизодные.

Сверка после возврата: сезоны совпали, эпизоды совпали — 8/34, как и было.

## Следствия для кода

1. `SonarrClient.set_season_monitoring` использует **POST**, а не PUT.
2. Успех определяется кодом ответа (202), а не телом.
3. Клиентская переработка пресетов не нужна и вредна — `_should_monitor_season`
   остаётся только для пути добавления (`add_series`), где флаги расставляет сам
   Sonarr по `addOptions`.
4. Порядок в `_execute_grab`: сначала `set_series_monitored(arr_id, True)`,
   затем `set_season_monitoring(arr_id, monitor)`.
